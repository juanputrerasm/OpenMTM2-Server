OpenMTM2 Server changelog
=========================

0.4.1 (2026-11-09)
------------------

Additions
- Relay rooms, for Community Patch 3 and 4 (docs/PROTOCOL.md "Relay rooms"):
  an opaque relay channel of binary frames tagged 0xC3 (a flags byte, a u16
  member id, up to 1200 bytes of payload). The server writes the sender's
  member id into every frame it forwards, so no client can speak as another,
  and sends it to one member or to all the others, in the lobby and in the
  race. 32768 bytes a second per connection, bursts of 65536
  (relayBytesPerSecond, relayBurst); frames past the rate or the size are
  dropped silently. Relay frames in an ordinary room are dropped.
- hello.caps: up to 16 capability names from the client. A client that
  declares cp3-relay/1 makes relay rooms (create relay: false for an ordinary
  one), and only clients that declared it may join one; the others get the
  new error code capability. Ordinary rooms stay open to every client. The
  server lists cp3-relay/1 in its features, the hello answer gives the relay
  limits, and rooms and the room list carry relay.
- Relay rooms run no server barriers: start goes straight to racing, loaded
  and result are answered and do nothing, there is no results message, and
  the owner's new finish message ends the race.
- profile.truckCrc: the CRC-32/MPEG-2 of the truck's POD, as the track's
  checksum, passed on in the member and in each race entrant.
- --test-room [name], --test-room-relay, --test-room-echo (testRoom,
  testRoomRelay, testRoomEcho; OPENMTM2_TEST_ROOM): a permanent public room,
  code TESTRM, made at start, owned by its first member, kept when empty; as a
  relay room, and optionally sending relay frames back to their sender.
- Game packet profiles (protocol/mtm2-packets.js): retail (0x0201), cp3
  (0x3400) and cp4 (0x3402), picked from the version in a player's 0x03 by
  profileForVersion; CP3_NET_VERSION, CP4_NET_VERSION. CP3's 65-byte 0x02
  (f32 radian angles and steering, u32 sender tick at +0x3D), CP4's 116-byte
  0x02 (and up to two older poses with their ages), CP4's 40-byte 0x14
  (raceId at +0x24), 0x26 progress and 0x27 collision (CP3 and CP4), 0x28
  race loaded and 0x29 race release (CP4). encodePacket, decodePacket,
  packetSize, stateFields and stateFromPacket take the profile as a last
  argument, retail by default; retail bytes are unchanged. Layouts from
  OpenMTM2 docs/CP4_EXE_ANALYSIS.md section 9.

Changes
- decodePacket is strict: a packet must have its profile's exact size
  (before, longer packets were read); others come back with kind null and a
  reason, the voice radio (0x89) too.
- Member ids are 1 to 65535 and wrap, skipping those in use, so they fit the
  relay frame's u16.

0.4.0 (2026-11-06)
------------------

Additions
- A new room setting, rules: the owner's game rules for OpenMTM2 0.6.6 as one
  flat object (the physics model, the computer trucks' behaviour and speed,
  the helicopter's race line drop, the selected extension's settings and the
  like). Names are letters, digits, dots, underscores and
  hyphens (an extension id such as race-rumble); values are text, a
  number or true/false; 2048 bytes as JSON at most. The server keeps it whole
  and sends it to every member with the room, as it does the other settings.

Notes
- OpenMTM2's Deathmatch (OpenMTM2 0.7.0) plays on this server as it is: its
  mode state and each machine's modeTruck (hit points, wheels, credits, and
  each truck's own wrecks, times wrecked and respawns) are relayed whole, and
  its host rules (ext.deathmatch.*) fit the rules setting. A full room's
  modeTruck is under half of a text frame (tests/room-messages.test.mjs).

0.3.0 (2026-10-30)
------------------

Additions
- A new race event, wheels: a truck's wheels under OpenMTM2's Wheels damage
  (lost and torn-away axles as bit masks, each wheel's wear, the repair and pit
  counts), sent by the client that drives the truck, like a damage code.
- Two room settings for it, wheels (on or off, default off) and wheelsRepairS
  (the seconds before the wheels go back on, 0 never; default 8), the owner's
  rule for the whole room.

0.2.0 (2026-10-29)
------------------

Additions
- A new race event, modeTruck: an extension mode's state for the trucks one
  client drives, sent as that client's vehicle (OpenMTM2's Combat judges each
  truck on the machine that drives it). Any player may send it for a vehicle it
  owns, like a damage code. OpenMTM2's Combat needs it in online rooms.
- Team chat: a chat message may name the sender's teammates (team, a list of
  member ids); the line goes to those of them in the room, marked team. The
  room's teams are the clients' to decide (an extension mode's, or the lobby's),
  so the server only routes. A classic player on the team gets it as a private
  line, the original game having no team chat. hello's features now lists
  teamChat, which clients check before offering a team channel.
- start is refused while a member has reported not having the room's track
  (content crc -1): that player could not race on it.

0.1.1 (2026-10-26)
------------------

Fixes
- Cloudflare Worker: truck state now reaches the other players. With recent
  compatibility dates, Workers deliver binary WebSocket messages as Blobs, which
  the server read as empty and dropped, so no player saw the others move. The
  server now asks for ArrayBuffers (binaryType) and still reads a Blob if one
  arrives.
- Rooms no longer outlive a lost connection. A Worker cannot send WebSocket
  pings, so a player whose connection died without a close stayed in their room
  for good, still owning it. The room server now drops any client it has heard
  nothing from for idleTimeoutS (default 120 s; 0 turns it off): the player
  leaves the room, which closes or passes to the next player.

Protocol
- New close code 4010: nothing heard from the client for idleTimeoutS.
  Clients should send "ping" every 15 s (OpenMTM2 0.6.2 does).

Settings
- idleTimeoutS (default 120).

Cloudflare
- wrangler.toml: Worker named "multiplayer", a welcome message, any page
  allowed to connect.
- docs/CLOUDFLARE-DEPLOY.md: a step-by-step deploy guide from a new account.

Tests
- A Blob frame test for the Worker and idle timeout tests for the room server.

0.1.0 (2026-10-21)
------------------

- First release: openmtm2d, the room server for OpenMTM2's online rooms
  (room protocol 1), with its DirectPlay gateway for classic rooms that
  Monster Truck Madness 2 itself joins.
- openmtm2-bridge, the desktop helper for classic DirectPlay and Community
  Patch 3 direct connect games.
- The room server as a Cloudflare Worker on the free plan.
